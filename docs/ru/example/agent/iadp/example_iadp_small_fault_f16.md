# F-16: iADP при небольшом отказе привода

Пример показывает, как **адаптивный регулятор** перестраивается после уменьшения коэффициента передачи команды стабилизатору на **15%**. Отказ возникает на 20-й секунде. Ноутбук теперь выполняет **500 секунд** моделирования; приведённые ниже исходные таблицы за 60 с сохранены для сравнения, длительная проверка описана в отдельном разделе.

- Ноутбук: `example/reinforcement_learning/incremental_adp/example_iadp_small_fault_f16.ipynb` — уже содержит результаты выполненного запуска.
- Скрипт: `example/reinforcement_learning/incremental_adp/example_iadp_small_fault_f16.py`.
- Агент: [iADP](../../../agent/iadp.md); объект: [нелинейная продольная F-16](../../../model/f16_nonlinear_longitudinal.md).

## Запуск

Из корня репозитория, в окружении с установленными зависимостями проекта:

```bash
python -m example.reinforcement_learning.incremental_adp.example_iadp_small_fault_f16
```

В `outputs/f16-small-fault/` появятся `comparison.png`, `comparison.svg`, `metrics.json` и полные CSV-траектории четырёх сценариев. Для показа окна добавьте `--show`; для другого каталога — `--output /tmp/f16-demo`.

```bash
# Меньший отказ и уточнение интегрирования при том же регуляторе
python -m example.reinforcement_learning.incremental_adp.example_iadp_small_fault_f16 \
  --loss 0.10 --substeps 2 --output /tmp/f16-demo-10
```

Доступны `--loss` от 0 до 0.20, `--fault-time`, `--duration`, `--phase` и `--substeps`. Время события и длительность должны быть кратны 0.02 с.

## Что именно ломается

Штатный `DamageProfile` применяет `control_failure / efficiency_loss` к общей команде стабилизатору:

\[
\delta_{\mathrm{target}} = \eta\,\operatorname{clip}
  (\delta_{\mathrm{trim}} + u, -25^\circ,25^\circ),
\qquad \eta = 1\ \text{до отказа},\quad 0.85\ \text{после}.
\]

Уменьшается **вся команда, включая балансировочную составляющую**. Поверхность не перемещается мгновенно: сохраняется штатный привод второго порядка с ограничениями 25° и 60°/с. Аэродинамические таблицы, масса и инерция остаются прежними. Это упрощённая модель потери коэффициента передачи привода, а не потеря 15% площади стабилизатора.

В продольной модели `stab_left` и `stab_right` адресуют один общий канал. Поэтому вводится **одно** событие на `stab_left`: это не асимметричный отказ левой половины. Два одинаковых события дали бы повторное ослабление команды.

Равновесие вычисляется численно: угол атаки около 4.918°, стабилизатор −4.447°. Скорость фиксирована на 150 м/с, высота — 3000 м. Управляемая величина — скорость тангажа, а не высота или траектория пространственного полёта:

\[
q_{\mathrm{cmd}}(t)=0.5\sin(2\pi\,0.12t)
+0.15\sin(2\pi\,0.31t+\varphi)\quad [^\circ/\mathrm{с}].
\]

## Как отделена адаптация от обычной обратной связи

Все четыре запуска имеют одинаковые начальные параметры и историю до события. В двух контрольных запусках на 20-й секунде фиксируются RLS-модель, её ковариация и матрица критика `P`. Измерения, история переходов, обратная связь и расчёт управления продолжают работать.

Адаптирующийся агент не получает время отказа, его величину или исправленную модель. Он использует скорость тангажа из наблюдения среды и усреднённое фактическое положение стабилизатора за интервал. Среднее вычисляется методом трапеций и является приближением эффективного входа с учётом движения привода.

Начальные `F`, `G` и `P` получены из **номинальной** линеаризации и дисконтированного DARE. Это обучение в процессе управления с подготовленной начальной политикой, не обучение с нуля. Реализация использует инкрементальную модель, RLS и оценку квадратичной функции ценности из [Konatala et al., 2024](https://doi.org/10.2514/6.2024-2402), раздел II. Эксперимент и способ задания отказа здесь собственные; это не воспроизведение их лётных испытаний.

## Сравнение iADP с PID, настроенным на исправном объекте

Вторая часть ноутбука сравнивает **два разных регулятора**. Отдельный запуск:

```bash
python -m example.reinforcement_learning.incremental_adp.example_iadp_vs_pid_f16
# Воспроизвести настройку PID исключительно на исправной F-16:
python -m example.reinforcement_learning.incremental_adp.example_iadp_vs_pid_f16 --retune-pid
```

Результаты сохраняются в `outputs/f16-iadp-vs-pid/`. По умолчанию используются коэффициенты уже выполненной номинальной настройки:

| Коэффициент | Значение | Единица |
|---|---:|---|
| Kp | −183.558823 | град / (рад/с) |
| Ki | −500.000000 | град / рад |
| Kd | −0.001307727 | град / (рад/с²) |

PID получает скорость тангажа в рад/с и выдаёт приращение команды относительно трима в градусах. Используется `tensoraerospace.agent.pid.PID`: производная по измерению, условное интегрирование при насыщении. В частности, отрицательные коэффициенты соответствуют отрицательному влиянию стабилизатора на ускорение тангажа.

Настройка выполнена на **отдельной 20-секундной траектории исправного объекта**, частоты команды 0.10 и 0.23 Гц. Целевая функция — среднее `error_rad_s² + R * applied_delta_deg²`, с тем же `R = 4.6861212294e-5`, что у iADP. Ограниченный поиск Nelder–Mead завершился за 60 вычислений. Диапазоны модулей коэффициентов: Kp ∈ [0.5, 300], Ki ∈ [0.5, 500], Kd ∈ [0.001, 50]. Ki достиг границы поиска; глобальный оптимум не заявляется.

При оценке используются другие частоты, 0.12 и 0.31 Гц. На 20-й секунде включается один и тот же отказ. **Kp, Ki и Kd больше не меняются**, но интегратор PID продолжает работать. iADP продолжает обновлять модель и критик. Ни один регулятор не получает сведения об отказе. Начальное состояние, задание, предел команды ±10°, ограничение приращения 60°/с относительно предыдущего измеренного входа и физический привод одинаковы. Это сравнение качества управления; затраты на предварительную настройку регуляторов не уравнивались.

![iADP против PID при отказе F-16](../../../../assets/images/iadp_vs_pid_f16.svg)

| Метрика ошибки скорости тангажа | iADP | PID |
|---|---:|---:|
| RMSE до отказа, 0–20 с, °/с | 0.0968 | 0.0095 |
| RMSE переходного процесса, 20–25 с, °/с | 0.7675 | 0.0647 |
| RMSE после отказа, 20–60 с, °/с | 0.3729 | 0.0252 |
| RMSE в позднем окне, 40–60 с, °/с | 0.2170 | 0.0112 |
| Максимальная ошибка после отказа, °/с | 1.2613 | 0.3585 |

**В этом сценарии номинально настроенный PID точнее текущей конфигурации iADP.** Выигрыш адаптации относительно замороженного iADP из первой части не означает превосходства над PID. Неизменные коэффициенты PID допускают изменение управляющей команды и компенсацию смещения интегральной составляющей.

Результат также проверен для потерь 10% и 20%, другой фазы команды, нулевого отказа и шага физики 10 мс при периоде управления 20 мс. Журнал номинальной настройки и все метрики: `reports/iadp-vs-pid-f16-validation.json`.

## Настроенный iADP и вариант с интегральным состоянием

В третьей части ноутбука добавлены два отдельных изменения: подбор параметров исходного iADP и расширение его состояния интегралом ошибки. Запуск:

```bash
python -m example.reinforcement_learning.incremental_adp.example_iadp_tuned_f16
# Повторить итоговый поиск 27 вариантов только на исправном объекте:
python -m example.reinforcement_learning.incremental_adp.example_iadp_tuned_f16 --search
```

Результаты: `outputs/f16-iadp-tuned/`. PID сохраняет прежние номинально настроенные коэффициенты.

### Почему недостаточно одного подбора коэффициентов

Подбор 61 варианта исходного iADP улучшил слежение, но оставил постоянное смещение после отказа. Уменьшение полной команды, включая трим, требует дополнительной постоянной компенсации. В исходном эксперименте состояние контроллера содержит только скорость тангажа; памяти об интеграле ошибки в нём нет.

В обсуждении *Fine-Tuning Controller Performance* [Konatala et al., 2024](https://doi.org/10.2514/6.2024-2402) авторы отмечают отсутствие интегральной информации в базовой стоимости и обсуждают расширение состояния/стоимости. Здесь проверяется **наша постановка с интегральным состоянием**, без изменения уравнений `IADPAgent` и без внешней PID-коррекции:

\[
z_{k+1}=z_k+\Delta t(q_k^{\mathrm{ref}}-q_k),\qquad
x_k=[q_k,z_k]^T,\qquad x_k^{\mathrm{ref}}=[q_k^{\mathrm{ref}},0]^T.
\]

Интегрирование причинное: используются измерение и задание в начале текущего шага. Задание будущего шага не используется для обновления интеграла.

### Выбранные параметры

| Параметр | iADP с интегральным состоянием |
|---|---|
| Q | diag(1, 30) |
| R | 2.3430606147 × 10⁻⁵, половина исходного R |
| gamma | 0.99 |
| gamma_rls | 0.9995 |
| phi_init | 20000 |
| policy_eval_window / min_samples | 300 / 300 |
| policy_eval_every | 10 шагов |
| policy_eval_blend | 0.0001 |
| Период управления | 0.02 с |

Номинальный поиск проходил по ошибке скорости тангажа и фактическому управляющему воздействию с **общим внешним весом R**, не зависящим от настроек кандидата. После первичного поиска интегральных весов выполнен дополнительный поиск 27 настроек на 60-секундной исправной траектории: короткие эпизоды не выявляли последующее ухудшение из-за обновлений критика. В целевую функцию поиска не входили данные после отказа. Итоговый поиск воспроизводится флагом `--search`.

### Результат при отказе 15%

![Настроенный iADP с интегральным состоянием против PID](../../../../assets/images/iadp_tuned_f16.svg)

| Контроллер | RMSE 20–60 с, °/с | RMSE 40–60 с, °/с |
|---|---:|---:|
| Исходный iADP | 0.372911 | 0.216974 |
| iADP, только подбор параметров | 0.172925 | 0.167507 |
| iADP + интегральное состояние | **0.023084** | **0.003771** |
| PID | 0.025177 | 0.011156 |
| iADP + интеграл, параметры заморожены после 20 с | 0.022632 | 0.003499 |

Интегральный вариант уменьшил RMSE относительно исходного iADP на **93.8%**, относительно PID — на **8.3%** за весь интервал после отказа. В позднем окне ошибка примерно в три раза меньше, чем у PID. Полоса ±0.05°/с достигается через **0.70 с** против **0.74 с** у PID; время измеряется до первого входа с удержанием полосы до конца эпизода, при минимум 5 с оставшегося наблюдения. Максимальная ошибка при этом немного больше, чем у PID: 0.368 против 0.359°/с.

**Это преимущество настройки и интегрального состояния, не доказательство пользы продолжения адаптации.** При фиксации параметров улучшенного iADP после события результат немного лучше. Интеграл продолжает обновляться и в этом контрольном запуске.

При отказе 10% интегральный iADP также точнее PID, но при отказе 20% PID лучше по общей ошибке переходного процесса. Проверки на длинных эпизодах и с уточнением интегратора, проигрыши и полная история поиска сохранены в `reports/iadp-f16-tuning-validation.json`.

## Проверки и границы результата

Сценарий останавливается с ошибкой при нечисловых состояниях/параметрах, неположительной ковариации, смене знака управляющего коэффициента, нарушении ограничений привода или выходе за выбранные пределы угла атаки и скорости тангажа. Тесты проверяют совпадение историй до отказа, заморозку параметров при действующей обратной связи, момент события и нулевой отказ.

Дополнительно проверены отказы 10% и 20%, другая фаза команды и эпизод длительностью 120 с. Численные результаты, включая неудачный исследовательский вариант, сохраняются в `reports/iadp-f16-small-fault-validation.json`.

**Период управления зафиксирован на 20 мс.** `--substeps 2` и `--substeps 4` уточняют интегрирование физики до 10 и 5 мс, сохраняя частоту управления и обучения. Простое уменьшение самого периода управления до 10 мс без перенастройки почти устранило выигрыш от адаптации: оно меняет в том числе окно обучения и ограничение приращения команды. Этот вариант не включён в поддерживаемые настройки примера.

Результат относится к данной модели, начальному режиму и настройкам. Здесь нет шума измерений, турбулентности и полной пространственной динамики; сходимость критика на произвольном горизонте не доказана.

## Неизвестное время отказа: непрерывное обучение

Заморозка в известный момент события выше используется только для диагностики. Новый пример сравнивает **непрерывно обучающийся iADP** и PID с фиксированными коэффициентами; расписание повреждений получает только окружение.

```bash
python -m example.reinforcement_learning.incremental_adp.example_iadp_fault_scenarios_f16
```

Проверены поздний отказ команды −15%, постепенная деградация до −20%, повторяющиеся отказы с восстановлением и симметричная потеря 30% обеих законцовок крыла. Два заранее определённых расписания, 20 запусков по 500 с, настройки регуляторов прежние.

![Непрерывный iADP при неизвестном времени отказов](../../../../assets/images/iadp_unknown_faults_f16.svg)

В позднем отказе, постепенной деградации и повреждении крыла PID точнее в обоих расписаниях. При повторяющемся отказе общая RMSE iADP меньше на 0.13% и 2.26%, но последние 100 с в обоих случаях хуже PID. Устойчивого преимущества текущей настройки не обнаружено.

Следующие приоритеты — отдельно смоделировать уменьшение аэродинамического действия стабилизатора при сохранении измерения его фактического угла и замедление привода. Аэродинамический вариант рассчитан в следующем разделе; замедление привода пока не проверено. Секционная модель повреждения крыла демонстрационная; она не валидирована по повреждённой реальной F-16.

Подробный протокол, физический смысл сценариев и результаты обоих расписаний: `reports/iadp-f16-unknown-faults-validation.md` и `.json`.

## Найденный выигрыш: аэродинамический отказ и непрерывное обучение

Новый выполненный notebook: `example/reinforcement_learning/incremental_adp/example_iadp_aero_effectiveness_f16.ipynb`.

```bash
python -m example.reinforcement_learning.incremental_adp.example_iadp_aero_effectiveness_f16
```

За 500 с моделирования в 137 с аэродинамическое действие фактически отклонённого стабилизатора уменьшается на 30%. iADP продолжает оба цикла обучения. Расписание доступно только окружению; переключения или сброса контроллера при событии нет.

![Выигрыш непрерывного iADP при аэродинамическом отказе](../../../../assets/images/iadp_aero_effectiveness_f16.svg)

| Метрика, °/с | iADP + интеграл | Усиленный PID |
|---|---:|---:|
| RMSE 137–500 с | **0.017749** | 0.020507 |
| RMSE 400–500 с | **0.006591** | 0.007840 |
| Пиковая ошибка после события | **0.818458** | 0.913131 |

Снижение RMSE — **13.45%** после события и **15.94%** в последние 100 с. iADP выбран из шести настроек только по исправному 500-секундному заданию: `policy_eval_blend=1e-6`, `gamma_rls=0.9999`. Критик обновляется медленно, но непрерывно; оценка управляющего влияния после отказа меняется примерно на 30%. PID перенастроен на исправном объекте с расширенными границами: Kp = −135.606952, Ki = −982.693451, Kd = −0.002070702. Прежний предел Ki = 500 больше не ограничивает сравнение. Затраты на настройку не уравнивались.

Выигрыш при отказе 30% сохранился для разных времён события, другой фазы задания и шагов физики 10 и 5 мс. **На исправном объекте и при отказе 40% PID лучше.** Это конкретный выигрыш данной конфигурации, не универсальное преимущество iADP.

Модель отказа: `C_fault(δ)=C(0)+eta*(C(δ)-C(0))` для подъёмной силы и момента. Привод и измерение его фактического положения остаются штатными. Это параметрическая проверка, не валидированная модель конкретного разрушения самолёта.
